# 个税 SEO 内容矩阵

## 1. 文档定位

本文档管理“极简个税”的搜索入口和内容生产，不替代产品需求和计算规则。产品范围见：[极简个税产品需求文档](./personal-income-tax-product-requirements.md)。

核心原则：每个页面既是一个可用工具，也是一个能独立回答搜索问题的内容页面。

## 2. 页面分层

### 2.1 核心工具页：优先开发

| 页面 | 主要关键词 | 目标 |
| --- | --- | --- |
| 工资薪金个税计算器 | 个税计算器、个人所得税计算器、工资个税计算器 | 获取核心需求流量 |
| 税后工资计算器 | 税后工资、工资到手、税后收入计算器 | 覆盖“到手多少”需求 |
| 年终奖个税计算器 | 年终奖个税、年终奖计算器 | 获取高峰期和高意图流量 |
| 税后反推税前工资 | 税后工资反推税前、税前税后换算 | 覆盖反向计算需求 |
| 专项附加扣除计算器 | 专项附加扣除、个税扣除能省多少 | 把政策解释转成可操作工具 |

### 2.2 所得类型页：长尾扩展

- 劳务报酬个税计算器。
- 稿酬个税计算器。
- 特许权使用费个税计算器。
- 财产租赁个税计算器。
- 财产转让个税计算器。
- 利息股息红利个税计算器。
- 偶然所得个税计算器。
- 个体工商户个人所得税计算器。

每个页面必须说明适用人群、计税时点、费用扣除方式、公式、示例和不适用的情况。

### 2.3 场景解释页：问题导向

- 年中入职个税怎么算。
- 换工作后个税怎么计算。
- 为什么年底个税变高。
- 工资一样为什么每月个税不同。
- 专项附加扣除怎么填。
- 子女教育和婴幼儿照护如何分配扣除。
- 年终奖单独计税还是并入综合所得。

### 2.4 城市页：与社保公积金联动

优先覆盖北京、上海、深圳、广州、杭州，再根据搜索和数据维护能力扩展。

城市页不只替换城市名，应包含当地社保和公积金基数、缴费比例、政策生效日期、计算示例和来源。数据缺失时不要生成伪精确结果。

## 3. 单页内容模板

1. 页面标题：明确工具名称、适用年份或场景；避免永久写死“最新”。
2. 首屏工具：用户可以直接输入并得到结果。
3. 结果解释：说明税额、税率或到手收入变化的原因。
4. 计算公式：用普通语言解释关键变量，再给出公式。
5. 适用范围：居民或非居民、按月或按次、预扣还是汇算。
6. 计算示例：使用真实可复核的输入和输出。
7. FAQ：回答该关键词下最常见的 4 至 8 个问题。
8. 相关工具：链接到前后相关的工具页和场景页。
9. 来源与免责声明：展示规则核对日期、政策来源和测算说明。

核心工资薪金页面还必须包含以下可索引内容模块：

- 个人所得税预扣率表：说明这是居民个人工资薪金累计预扣预缴适用的税率表。
- 税务知识：累计预扣法、工资与缴费基数的区别、年底个税变化原因、专项附加扣除等。
- 常见问题：围绕计算结果、城市规则、缴费基数、年度预扣与年度汇算的真实问题。
- 官方来源：税率表、累计预扣法、专项附加扣除标准和规则核对日期。

这些内容必须以服务端渲染或静态 HTML 形式出现在页面中，不能只在用户点击计算后通过客户端脚本生成，否则搜索引擎和未执行脚本的抓取工具可能看不到核心内容。

## 3.1 工具页的 SEO 实现方式

计算器页不是一张孤立的表单，而是一套可复用的页面模板：

```text
页面标题 / 描述 / H1
├── 可直接使用的计算器
├── 本月结果和结果解释
├── 当月五险一金汇缴明细
├── 全年走势和 12 个月明细
├── 个税税率表
├── 税务知识
├── FAQ
├── 官方来源与规则核对日期
└── 相关工具和城市内链
```

推荐 URL 结构：

```text
/salary-tax-calculator/
/salary-tax-calculator/city/beijing/
/salary-tax-calculator/city/shanghai/
/bonus-tax-calculator/
/after-tax-to-before-tax/
```

城市页面必须拥有独立的城市规则、基数范围、案例、FAQ 和来源，不能只替换标题中的城市名称。城市数据不足时不生成页面，避免大量低质量重复页。

技术 SEO 最低要求：

- 每个页面独立配置 `title`、`description`、canonical 和 H1。
- 工具页使用 `WebApplication` 结构化数据；有可见 FAQ 时再使用 `FAQPage`。
- 增加 `BreadcrumbList`、站点地图和规范的 robots 配置。
- 计算器的交互逻辑可以在客户端运行，但税率表、知识、FAQ、来源和核心解释必须在首屏 HTML 中可读取。
- 页面规则版本、城市政策生效日期和最近核对日期可配置。
- 统计曝光、点击、计算完成率、结果解释展开率、税率表阅读和相关工具点击。

## 4. 站内链接结构

建议形成三层结构：

```text
首页/工资薪金计算器
├── 税后工资与税前反推
├── 年终奖计算器
├── 专项附加扣除计算器
├── 所得类型工具
├── 城市社保公积金页面
└── 场景解释与 FAQ
```

每个专题页至少链接回一个核心工具页，并链接到两个相关专题页。核心工具页链接到高价值 P1 页面，避免所有页面只互相堆叠关键词。

## 5. 发布顺序

### 第一批：建立核心入口

- 工资薪金个税计算器。
- 税后工资计算器。
- 年终奖个税计算器。
- 专项附加扣除计算器。
- 3 至 5 篇“为什么年底个税变高”“年中入职个税怎么算”等解释页。

### 第二批：扩大真实场景

- 税后反推税前工资。
- 劳务报酬个税计算器。
- 稿酬和特许权使用费个税计算器。
- 北京、上海、深圳、广州、杭州城市页。

### 第三批：补充长尾

- 财产租赁、财产转让、利息股息红利、偶然所得。
- 更多城市和工资档位案例。
- 按行业或用户身份组织的专题内容。

## 6. SEO 质量要求

- 每个页面有独立的 `title`、`description`、H1 和正文，不复制通用段落。
- 页面首屏优先满足搜索意图，文章内容不能遮挡工具。
- 公式、税率表、FAQ 与实际计算逻辑使用同一规则版本。
- 页面年份、政策状态和规则核对日期可配置。
- FAQ 只回答页面实际支持的情况；不为获取关键词而承诺尚未实现的功能。
- 结构化数据按页面类型配置，工具页、FAQ 页和文章页不要混用不匹配的类型。
- 记录曝光、点击、计算完成率、结果展开率和相关工具点击率。

## 7. 页面验收清单

- 用户是否能在 10 秒内找到输入区？
- 用户是否能看懂结果中的“本月”“累计”“全年”区别？
- 页面是否解释了结果为什么变化？
- 页面是否说明适用范围和不适用情况？
- 页面是否有至少一个官方来源和规则核对日期？
- 页面是否链接到核心工具和两个相关页面？
- 输入、公式、示例和 FAQ 是否使用同一套测试数据？
