# 极简个税产品需求文档

## 1. 文档定位

本文档是“极简个税”产品的总需求文档，负责定义产品目标、用户流程、功能范围、页面结构和迭代优先级。

政策计算口径见：[个人所得税计算规则与数据口径](./personal-income-tax-calculation-rules.md)。

SEO 页面、关键词和内容生产规则见：[个税 SEO 内容矩阵](./personal-income-tax-seo-content-matrix.md)。

竞品研究记录见：[个税竞品分析记录](./personal-income-tax-competitor-analysis.md)。

社保、公积金及企业用工成本规则继续沿用：[社保、公积金与企业用工成本规则需求文档](./social-housing-contribution-rules-requirements.md)。

## 2. 产品结论

不建议把所有内容写进一份不断膨胀的文档，也不建议一开始拆成过多零散文档。

采用“一份总需求 + 两份专题文档 + 一份已有基础能力文档”的结构：

| 文档 | 负责内容 | 主要读者 |
| --- | --- | --- |
| 本文档 | 产品定位、用户流程、功能范围、页面结构、优先级 | 产品、设计、开发 |
| 计算规则与数据口径 | 公式、税率表、边界条件、政策来源、测试样例 | 开发、测试、内容 |
| SEO 内容矩阵 | 关键词、页面类型、内容模板、内链和发布顺序 | 产品、内容、SEO |
| 竞品分析记录 | 竞品能力、图表、城市规则和产品启发 | 产品、设计、运营 |
| 社保规则需求 | 城市政策版本、基数、缴费项目、采集和规则数据模型 | 后端、数据、运营 |

原因：个税计算的政策口径属于高风险共享能力，需要独立维护；SEO 页面数量会持续增长，不应反复改动产品主需求；社保规则已经有独立数据模型，个税产品只需通过接口或模块引用。

## 3. 背景与机会

现有竞品大致分成三类：

1. 内容 SEO 型：以 `gerensuodeshui.cn` 为代表，工具之外有税率表、公式、案例、资讯、城市和热门标签，长尾覆盖较完整。
2. 收入类型覆盖型：以 `m.geshuiba.com`、`hkttt.prthwyp.com` 为代表，覆盖工资、年终奖、劳务报酬、稿酬、特许权使用费、财产租赁等多种所得。
3. 产品化工资计算型：以 `webfem.com/tools/tax-calculator/index.html`、`geshui.dwzry.com` 为代表，输入和结果界面更现代，部分产品支持社保、公积金和逐月测算。

竞品共同问题：

- 计算结果通常只有数字，缺少“为什么是这个数字”的解释。
- 工资薪金的累计预扣法、月度简单估算、年终奖单独计税容易被混在同一页面里。
- 部分页面的年份、专项附加扣除标准或税率展示不够可靠。
- 许多工具输入项多，首次使用成本高；另一些工具过于简单，无法解释年底税额变化。

产品机会是做“最容易看懂的工资到手和全年个税测算”，以可信口径、少量输入、逐月解释和长尾场景内容建立差异化。

## 4. 产品定位

### 4.1 核心用户

- 想知道税后工资和全年个税的普通上班族。
- 年中入职、换工作、收入变化或年底发现个税增加的用户。
- 需要比较年终奖单独计税与并入综合所得的用户。
- 有子女教育、婴幼儿照护、住房租金、住房贷款利息、赡养老人等扣除需求的用户。
- 需要估算劳务报酬、稿酬或其他收入预扣税的自由职业者和内容创作者。

### 4.2 产品主张

> 输入工资和必要扣除，快速看到税后收入、全年结果，并且知道每个结果为什么这样算。

不把产品定位成“税务申报工具”，而是定位为“个人税费测算和解释工具”。所有结果页面都应明确：仅供测算，最终以个人所得税 APP、扣缴单位或税务机关口径为准。

## 5. MVP 范围

### 5.1 P0：首个可用版本

- 首页工具导航：展示工资薪金、年终奖、税后反推、专项附加扣除、税率表、FAQ 等模块的简短说明和入口；首页负责发现和分流，工资计算器仍是默认主入口。
- 工资薪金月薪计算器。
- 选择纳税年度、入职月份或当前计算月份。
- 税前月薪，P0 先支持全年固定月薪；逐月填写不同收入列入 P1。
- 个人社保和公积金：支持手动输入；城市规则接入后支持自动估算。
- 支持选择城市；每个城市有独立 URL 和规则页，便于城市 SEO 和政策版本维护。
- 城市选择支持手动选择和自动定位；自动定位需要用户授权，失败时必须保留手动选择入口。
- 社保缴费基数支持自动按工资估算，也支持手动覆盖，并显示城市允许范围。
- 公积金缴费比例可选，首期支持 3% 至 12%，具体选项按城市规则配置。
- 社保基数和公积金基数分开维护，不能默认认为两者相同。
- 基本减除费用、专项扣除、专项附加扣除和其他扣除的输入。
- 输出税后工资、本月个税、累计个税、适用税率、速算扣除数和全年估算。
- 逐月明细表，展示收入、扣除、累计应纳税所得额、本月税额和到手工资。
- 结果解释器，至少覆盖“未缴税”“税率跨档”“扣除影响”“年底税额上升”四类原因。
- 公式、税率表、规则生效日期和官方来源链接。
- 免责声明和规则核对日期。
- 统一图标规范：通用功能图标优先使用 Lucide；品牌图形和特殊业务图标在 Lucide 无合适语义时再通过 Figma 定制。

### 5.1.1 P0 待实现与验收补充

- 计算口径必须版本化：结果至少关联纳税年度、城市规则版本、规则生效日期和税率表版本；规则更新不能静默覆盖历史结果。
- 明确金额舍入规则：个人缴费、单位缴费、各项小计、社保公积金合计和个税分别规定计算精度与展示精度。
- 完成边界输入校验：工资为 0 或负数、基数超出城市范围、计算月份早于入职月份、专项扣除超过收入等情况必须有明确提示，不能静默产生伪精确结果。
- 完成规则缺失状态：城市规则未配置、规则过期或数据加载失败时，停止自动估算并保留手动填写入口。
- 明确全年结果口径：页面所有位置统一说明“全年个税”是全年预扣合计估算，不等同于年度汇算最终结果。
- 完成响应式与可访问性验收：单列布局不能遮挡结果，表格可横向查看，输入项可用键盘操作，错误提示可被辅助技术读取。
- 建立固定测试样例：至少覆盖税率临界点、年中入职、社保和公积金基数不同、公积金 3%/12%、专项扣除、城市切换和规则版本切换。
- 自动定位作为渐进增强：必须取得用户授权；定位失败、拒绝授权或浏览器不支持时，手动选择城市仍可完成计算。

### 5.2 P1：高价值场景

- 年终奖单独计税与并入综合所得对比。
- 税后工资反推税前工资。
- 年中入职和换工作场景。
- 逐月填写不同收入并重新计算全年预扣结果。
- 专项附加扣除节税测算。
- 北京、上海、深圳、广州、杭州等重点城市的社保公积金自动估算。
- 结果复制、分享链接或下载明细。

### 5.3 P2：SEO 长尾和收入类型扩展

- 劳务报酬个税计算器。
- 稿酬个税计算器。
- 特许权使用费个税计算器。
- 财产租赁、财产转让、利息股息红利、偶然所得计算器。
- 个体工商户和承包承租经营所得测算。
- 城市、工资档位和典型案例页面。

## 6. 核心用户流程

### 6.1 工资薪金测算

1. 用户进入页面后直接看到工资计算器，不需要先阅读长说明。
2. 用户输入税前月薪、月份和必要扣除，点击“开始计算”。
3. 页面先展示税后收入、本月个税和全年估算。
4. 结果下方给出一句结论，例如：

   `你在 8 月的累计应纳税所得额超过 36,000 元，进入 10% 预扣率档位，所以本月个税比上月增加。`

5. 用户可展开查看逐月明细、公式和扣除影响。
6. 页面提供年终奖、税后反推、专项附加扣除等相关入口。

### 6.2 结果解释规则

结果解释器必须使用计算过程中的真实数据生成文案，不使用与结果无关的固定宣传语。

至少支持：

| 触发条件 | 解释方向 | 示例 |
| --- | --- | --- |
| 本月应纳税额为 0 | 扣除后未超过起征水平 | 累计扣除后应纳税所得额未超过 0，本月无需预扣个税。 |
| 适用税率高于上月 | 累计应纳税所得额跨档 | 累计应纳税所得额超过 36,000 元，本月进入 10% 预扣率档位。 |
| 专项附加扣除增加 | 扣除降低应纳税所得额 | 本月新增专项附加扣除，预计减少应纳税所得额，并降低应预扣税额。 |
| 年末税额明显上升 | 累计收入增长快于累计扣除 | 年末累计收入增加较快，累计预扣法会在本月补足前期少预扣部分。 |
| 社保公积金变化 | 扣除基数或比例发生变化 | 社保公积金扣除变化影响了本月应纳税所得额。 |

## 7. 页面结构

### 7.1 首页 / 工资薪金计算器

首屏直接可用，建议结构：

- 顶部：品牌、核心工具入口、规则核对日期；首页入口使用图标辅助识别，但必须保留文字标题。
- 首页工具入口区：每个模块提供一个简短说明和明确入口，覆盖工资薪金、年终奖、税后反推、专项扣除、税率表、FAQ 和其他所得扩展。
- 输入区：收入、月份、社保公积金、专项附加扣除。
- 结果区：税后工资、本月个税、全年个税。
- 解释区：一句结论 + 触发原因。
- 明细区：当月五险一金汇缴明细和 12 个月逐月表格。
- 年度趋势不单独做重复图表；优先通过 12 个月逐月明细呈现变化，只有出现明确解释价值时再增加图表。
- 基数区：社保、公积金基数默认直接展示，标签旁提供“编辑”按钮，点击后才进入可编辑状态。
- 规则区：公式、税率表、适用范围、官方来源。
- 内容区：典型案例、FAQ、相关工具和长尾页面入口。
- SEO 内容区：个人所得税税率表、税务知识、常见问题、官方来源和规则核对日期。

首页入口区不承担复杂计算，重点是让用户快速理解“这里能解决什么问题”。图标优先采用 Lucide 现成图标；不能为了装饰堆叠图标，也不使用没有文字说明的图标按钮。

### 7.2 其他工具页

每个工具页都遵循“工具在前，解释在后”的结构：

1. 首屏工具。
2. 结果解释。
3. 计算公式和适用范围。
4. 示例结果。
5. FAQ。
6. 相关工具和内链。

SEO 页面不能只放一个表单，也不能只复制一份通用文章。页面需要回答该关键词对应的真实问题。

## 8. 功能需求

### 8.1 输入

- 所有金额输入支持数字键盘、千分位展示和两位小数校验。
- 必填字段尽量控制在 2 至 4 个；高级字段默认折叠。
- 修改任意输入后，结果可即时刷新或通过明确按钮刷新，交互方式保持一致。
- 计算月份、纳税年度和入职月份必须互相校验。
- 对“税前工资”“税后工资”“累计收入”“本月收入”提供短说明，避免术语歧义。

### 8.2 结果

- 结果数字使用人民币格式，保留两位小数或按产品统一规则展示。
- 明确区分“本月预扣税额”“年度累计预扣税额”“全年最终应纳税额估算”。
- 显示适用税率和速算扣除数，但不能只展示表格而不解释。
- 月度明细能追溯到收入、扣除、累计应纳税所得额和税额变化。
- 企业缴费只在当月五险一金汇缴明细中展示，不在结果卡重复展示企业成本摘要。
- 支持空结果、输入错误、数据不足和规则未覆盖城市等状态。

### 8.3 规则和来源

- 每套规则保存生效时间、来源 URL、来源标题、核对日期和备注。
- 前端显示“规则核对日期”和“适用范围”。
- 规则更新不能覆盖历史版本。
- 计算失败或规则缺失时，不展示看似精确的默认结果，应明确提示原因。

## 9. 非功能要求

- 移动端优先，核心输入和结果在常见手机宽度下无需横向滚动。
- 首屏加载后可在无登录状态下完成计算。
- 页面标题、描述、canonical、结构化数据和站内链接可配置。
- 计算逻辑应有单元测试，至少覆盖税率跨档、月中入职、专项附加扣除、年终奖两种计税方式。
- 计算结果应可复现：相同输入、相同规则版本得到相同结果。
- 不采集身份证号、银行卡号等不必要的敏感信息。

## 10. 迭代优先级

| 阶段 | 交付物 | 验收重点 |
| --- | --- | --- |
| Phase 1 | 工资薪金计算器、累计预扣、结果解释、公式和来源 | 计算可信、输入少、结果看得懂 |
| Phase 2 | 年终奖对比、税后反推、逐月收入、重点城市规则 | 覆盖高频真实场景 |
| Phase 3 | 劳务报酬及其他所得类型、SEO 内容矩阵 | 扩展长尾流量和复用能力 |
| Phase 4 | 规则后台、来源核对、数据更新提醒、用户反馈闭环 | 降低政策更新成本 |

## 11. 验收标准

- 用户可以在首次打开页面后，不阅读说明就完成一次基础工资测算。
- 结果页同时回答“到手多少”“交多少税”“为什么是这个数”。
- 工资薪金默认使用累计预扣预缴口径，不把月度速算公式当作默认口径。
- 专项附加扣除标准、税率表和规则来源能追溯。
- 关键边界案例有固定测试样例，并且结果变化可解释。
- SEO 页面具备独立标题、独立正文、独立 FAQ 和相关工具内链。

## 12. 风险与待确认事项

- “全年个税”要明确是全年预扣合计，还是年度汇算最终应纳税额；MVP 默认展示全年预扣估算，并在文案中明确区别。
- 社保公积金自动估算依赖城市、政策年度和缴费基数，必须允许用户手动覆盖。
- 年终奖计税政策存在期限和政策变化，不能在页面标题中永久写死“最新”。
- 劳务报酬等所得类型涉及按次预扣、居民与非居民等差异，需要在专题规则文档中定义边界后再开发。
- 所有结果仅供测算，最终以个人所得税 APP、扣缴单位或税务机关口径为准。
